# 戦績の同一試合判定（report_version=2）

## 目的と移行

PC 時計のずれ、通信の再送、同期の遅延によって別の試合を統合しない。
サーバーを更新してから対応クライアントを配布する。新クライアントは
`GET /matches/protocol` の `report_version: 2` を確認し、未対応サーバーには
v2 の戦績を書き込まない。送れなかった結果はローカル SQLite に残す。
この変更だけで既存の誤った戦績やランクを自動修復することはない。

## ID と時刻

- `client_id`: クライアントが試合開始時に一度作る32桁の小文字hex ID。
  ローカル行の主キー、即時報告、再送、まとめ同期で同じ値を使う。
  KO の勝敗変化や一瞬のシーン変化では新しい ID を作らない。
- `match_id`: サーバーが発行する両者共通の32桁hex ID。募集IDではなく1試合のID。
  DB の確定戦績の主キーにもなる。参加者以外はこのIDで報告・リプレイを登録できない。
- `played_at`: PCの壁時計による申告値。監査用に原文とともに保存する。
- `received_at`: サーバー受信時刻。再送では最初の受信時刻を維持する。
- `start_age_sec` / `duration_sec`: 単調増加時計で計測した開始からの経過秒数。
  確定戦績の時刻は開始受付時刻から補正した開始時刻＋対戦時間で決める。
  過去のまとめ同期を、同期した「今」の試合として扱わない。

## 開始と照合

`POST /matches/presence` に通常のプロファイル・`my_side` とともに
`client_id`, `start_age_sec`, ホスト側は `post_id` を送る。
認証済みの参加者、募集接続、ホスト/ゲストの役割、両プロファイル、開始時刻の
整合性（補正後3秒以内）が一意に確認できる開始申告にだけ、同じIDを返す。
開始が先に届いた側にはサーバーが新しいIDを発行し、相手が参加する。
試合終了後・次の試合の開始後の申告を過去の開始に結び付けない。
開始の再送は永続化した同じIDを返す。サーバー再起動でもIDは失われない。

同定前のクライアントは2秒間隔で再試行する。接続が見つからない場合は10秒待ち、
単独利用用のIDを発行する。初回開始申告が30秒より遅い場合や、両者のIDが
一致しない場合は、結果から開始を推測して過去の試合へ結び付けない。
終了解除の申告は同じ `client_id` と `ended: true` を使う。
両者が asobby 利用者として同定されているのに片側が未対応・未申告なら結果は保留する。
片側のみ asobby 利用の場合は、その側の報告からカジュアル戦績を記録できる。

## 結果・同期・リプレイ

`POST /posts/result` と `POST /matches/report` に以下を追加する。
既存の所有者トークン/Discordセッションの認証は維持する。

```json
{
  "report_version": 2,
  "client_id": "0123456789abcdef0123456789abcdef",
  "match_id": "abcdef0123456789abcdef0123456789",
  "duration_sec": 125.5
}
```

`match_id` の応答を失った場合は空文字でもよい。サーバーに保存された
本人の `client_id` から解決する。開始IDがない報告は保留する。
`POST /matches/sync` の各要素も同じ4フィールドを送る。再送や同一バッチ内の
重複で確定戦績やレートを二重計上しない。

応答の `accepted: true` は元報告の永続化完了であり、戦績確定とは異なる。

| status | recorded | 意味 |
| --- | --- | --- |
| pending | false | 相手の結果待ち、開始未確認、旧版の曖昧な報告など |
| conflict | false | 同じIDで勝敗・キャラ・スコア等が食い違う |
| confirmed | true | 1件の戦績として確定。再送では duplicate=true |

未確定報告は `match_reports` に置き、公開戦績・ランク集計に入れない。
双方が参加したIDでは双方の結果の一致を待つ。確定済みの結果を変更した再送は
矛盾として保存し、既存の確定戦績・時刻・レートは上書きしない。
確定行の挿入と Ph のレート更新は同じDBトランザクションで行う。
DBの参加者行ロックと一意制約も使用し、プロセス内ロックだけに依存しない。

`GET /matches/reports`（Discord認証）で本人の状態を確認できる。
`client_id` クエリを最大100個指定でき、`limit` は1〜500、既定100。
各項目には `client_id`, `match_id`, `status`, `reason`, `received_at`,
`client_played_at`, `has_conflict`（変更された再送の有無）、確定時の `match`（未確定ならnull）が入る。
クライアントはこれを使い、後から確定した古い試合も取り込む。
ローカル履歴では保留を `…`、矛盾を `!` とし、勝率計算には含めない。

`POST /replays/upload` は `match_id` または本人の `client_id` クエリで
確定戦績を指定する。ID付きで該当しない場合、近い時刻の別試合にはフォールバックしない。

## 旧クライアント

IDのない経路は互換受付を残すが、完全な照合保証はできない。
ライブ報告の申告時刻が受信時刻から90秒よりずれる場合は保留する。
既存行との統合には、申告時刻3秒以内・参加者との整合・同じ勝敗とキャラが必要。
付近の候補が曖昧な報告や新旧混在の報告は保留し、直近180/600秒のプロファイル一致
だけで過去の行に強制統合する処理を廃止した。既存時刻はホスト報告で上書きしない。
旧版の保留報告がまとめ同期で再登録される迂回経路も防ぐ。

## 既存データの監査・修復

0016のマイグレーションは新しい表と索引を追加するだけで、既存戦績を改変しない。
まずバックアップを確保し、次の読み取り専用ツールで対象ユーザー・時刻を限定する。

```sh
cd server/app
PYTHONPATH=. python tools/audit_match_identity.py --user DISCORD_ID \
  --from 2026-09-18T19:29:00+00:00 --to 2026-09-18T19:51:00+00:00
```

両側のクライアントログ・サーバー診断ログと比較して、正しい試合、重複行、時刻、
リプレイの対応を確定する。その対応表を確認してから、個別のトランザクションで補正し、
ランクとPhレートへの影響も確認する。時刻が近いという理由だけで削除・統合しない。
従来の `merge_duplicate_matches.py --apply` は今回の修復には使用しない。
